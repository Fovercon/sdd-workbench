# 第一次使用

安装后在你的项目目录新开一轮 agent 对话。先选一个真实、范围清楚的小任务，不需要先记住
12 个技能名，也不需要先建立整套 Spec/Plan。仍要遵循项目规则与实际权限。
安装方法见 [README](../README.md#安装)，宿主发现与运行能力的验证范围见
[兼容说明](AGENT-COMPATIBILITY.md)。

## 从你要完成的事开始

下面的话直接发给 agent。尖括号里的内容换成你的事实；不知道的业务含义要说明不知道，
不要为了启动流程补一个猜测。终端安装命令不等于这些对话请求。

| 你现在要做什么 | 可直接使用的请求 | 应得到什么 |
|---|---|---|
| 清楚的局部 bug/小改动 | “用 SDD Workbench 处理这个局部问题：<现象>。正确行为是 <依据>，相关位置 <已知文件或入口>。请实际修复、做相应回归并说明结果。不要提交或发布。” | 实际修复与可核验结果；保留用户文件。若项目/风险不要求，不新建整套 Spec/Plan/看板。 |
| 新功能或需求还不清楚 | “我想让 <使用者> 在 <场景> 完成 <目标>。已知约束是 <事实>；不确定的是 <问题>。先整理需求，只问影响产品行为的问题。” | 明确需求、缺失输入与审批状态；不编造费率、格式或业务规则，不自行开始实现。 |
| 已有需求，要继续交付 | “按 <当前需求/计划的位置> 继续完成 <范围>。允许 <实现/测试/本地交付>；我保留 <需要本人批准的事项>。先核对当前证据。” | 从真实断点继续；保留已有合同、用户审批与未完成义务。明确是否还需批准或设计决定，不把计划当交付。 |
| 只想看代码质量 | “评审 <diff/提交/文件范围>，重点看 <风险>。可以运行 <允许的检查>，先不要修复。” | 具体问题、后果、位置和证据；有批准规格时按规格核对，无规格时不编造需求。 |
| 只想知道进度 | “现在 <具体任务> 做到哪里？依据是什么，还缺什么？只报告，不修改文件。” | 当前事实、缺证据和下一动作；不生成看板、规范或实现，不把缺失验证说成通过。 |
| 想看到项目图与证据 | “生成 <项目/模块范围> 的项目看板，展示业务流程、模块关系、下一动作和来源依据。” | 基于实际来源的图和快照；不会因为生成视图要求先走完整工程流程。要直接提交反馈时再说明。 |

边界由风险和实际合同决定，不能按字数判断：改一个费率、删除条件、数据迁移或安全权限，
即使只有一行，也可能需要先确认业务语义、设计与回退。明确保留的批准不会被“轻量”跳过。

## 一次任务完成时你应能核对的东西

1. **结果**：现在能做什么；是否真的改了、跑了，还是仅提出方案。
2. **证据**：实际检查及结果；未执行项和原因；需要时可找到文件/报告。
3. **边界**：你的文件和显式批准是否保留，是否还有未完成义务。
4. **下一步**：若有阻塞，应是具体缺失输入/决定；若任务已完成，不应停在“我可以继续”。

新产生的规格/计划应给出位置和真实状态。AI 推导、技术委托与人工批准应明确区分，
不必先学习它们的内部英文状态码才能做决定。提交、发布、部署和清理有各自的授权边界。

## 卡住或行为不符合预期

- **看不到技能**：先重开/重新加载宿主，按兼容说明核对实际发现目录和是否有同名旧副本。
  完整源码/Release ZIP 可运行 `python3 -B tools/doctor.py --agent all`，按[诊断说明](DOCTOR.md)
  检查文件和回执；客户端实际发现仍须单独验证。
  记录宿主与版本、安装方式和现象；不要直接覆盖个人修改或混用多种安装管理器。
- **装上了但命令跑不了**：复制实际命令、错误、环境与允许的工具范围。安装不自动补齐
  Python、浏览器、网络或项目依赖权限。没有执行不能当通过。
- **问了你已经回答的问题**：指出原始回答及适用范围，让 agent 重新核对已有授权和版本。
  若它问的是新业务决定/你保留的批准，应说明那个具体问题，而不是一律跳过。
- **小任务生成大量文档**：先让 agent 说明哪项风险、项目规则或合同要求这些产物，再按
  事实缩小流程；有真实高后果风险时不删除必要检查。
- **需要交给其他 agent/专家**：先保存当前任务、版本和实际证据；使用
  [审查包](optimization/REVIEW-KIT.md) 给出可复现记录。不要把整段聊天当唯一依据。

本指南是入口，不是公司政策或可靠性认证。当前优势假设、未解决的推广条件和优化顺序见
[基线审视](optimization/BASELINE-REVIEW.md)与[计划](optimization/PLAN.md)。
