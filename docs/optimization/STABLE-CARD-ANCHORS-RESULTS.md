# 稳定执行卡引用优化结果

本轮保留三个运行文件的改动。Plan 为新卡片版本生成真正且稳定的标题锚点，
把人类标题和当前/关闭状态放在正文；Implement 在回执中使用相对该回执的
Markdown 链接引用实际卡片。已有稳定位置、冻结卡片字节和权限来源保持其原有规则。

这是卡片引用可靠性的修复。重复检查记录和原始输出保留仍有问题，未证明整体降本。

旧模板以 `tasks.md#card-s02-v2` 举例，却实际生成带可变标题的 Execution Card。
上一轮两个项目分别写出了从未存在的逻辑锚点，以及关闭时改名而失效的旧锚点。

对照为开发提交 `4f79ffe`，候选为 `660ad2c`。两版各五个新会话，从相同初始文件
和同一普通完整开发请求开始，实际做完两个切片。未在请求里提示卡片锚点的答案或
指定记录器。所有十次都在首次写卡片前实际收到 Plan 主文、模板和 Implement 主文。

因此不能把这次结果说成所有卡片标签都已转为链接。五份候选的旧卡片执行条款均保留，

写入调用增加、重复明细未减少。输入和请求的下降只是本批观察：样本各五份，且
对照有两份自然选用记录器、候选没有。这些差异不能归因于卡片锚点，也不能把更小的

原始输出完整度在候选中更差，另有一份候选缺少初始 RED 的所测源码身份。表中的
三十个检查角色包括每片 RED、GREEN 和回归；一次真实调用可以覆盖两个角色，
不因此虚构成两次运行。本轮只保留已证实的卡片导航修复，原始证据与所测版本信息
仍需优先处理，不能将更易找到卡片等同于更完整的证据链。

## 新会话接手与兼容性

两版预先各选 t1–t3，每份交给两个新只读会话，使用相同的改动前运行时。候选
6/6 直接找到原 S01 卡片；对照 4/6 经搜索找到，另 2/6 正确指出原详细卡片已丢失。
十二个读者都找回文档中记录的 S01 RED/GREEN 命令与结果，并区分历史记录和当前
源码适用性。这不等于十二次都拿到了原始执行输出：实际可取回原始输出的是
对照 4/6、候选 2/6。一个候选读者另把 S02 的 16 次原始失败静态推成了 15 次。
一次对照读者在私有临时目录写入后删除文件，虽期末为空仍计入写范围失败。

另做三个固定候选兼容项目，覆盖原布局、自定义治理目录与嵌套回执、被哈希封存的
自定义历史卡片。六份自足回执的真实卡片链接从首次保存到最终均正确，完整命令、
结果、源码及测试身份与十八个真实检查子进程相符。三个产品均通过独立检查，
十二个交付示例正确，所有用户提供的冻结字节未改。旧 `CURRENT` 快照保持原样，
当前权限单独建立。指定兼容目标为 3/3，整体流程并非三份无缺陷通过：一份越界
写入并删除临时文件，另一份提前展开未来卡片，并修复了非卡片引用及执行设置问题。
自定义布局 t2 还在 Tasks 变动后改写了自建 Plan 基线回执，将其中原 Tasks 整文件
哈希替换为活记录说明。外部原生历史保留原稿和修订，不能据此宣称所有历史哈希引用
均已保全；用户提供的冻结输入确实保持原字节。

候选 t5 还覆盖了第一次 S02 的原始失败输出。它在同一生产源码上先失败 21 项，
添加一条测试后失败 22 项，两次都写同一个 `s02-red.txt`。控制器保留两次原生回执，
但交付树只剩第二份；稳定卡片引用没有解决这个原始证据缺口。
