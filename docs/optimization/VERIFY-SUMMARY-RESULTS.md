# 校验输出与摘要往返优化结果

本报告检查 `evidence.py verify --summary` 是否能减少手写摘要和回传负担，同时保留
真实校验退出码、历史记录与当前源码状态。它评估的是框架工具的使用效果。

对照为 `150958e`，候选为 `1989dc7`。运行时只改现有脚本与记录指南，新增可选
参数；默认 JSON、校验逻辑及记录器行为不变。指南示例选择紧凑模式，主文没有增加
工作步骤。开发分支保留这一可选入口与指南示例：默认兼容及诊断保留通过，真实
手写摘要减少。但一位接手者误读了新输出的计数和省略范围，接手成本也反增；
全语义、阶段/权限与标准门槛没有全部通过，不认定整体降本完成或发布就绪。

## 为什么试验这一项

上一轮修订版五份开发有 74 次真实校验，25 个 bash 调用自行用 JSON 摘要，覆盖
51 次校验。六份读者另有 11 次，三个兼容项目另有 25 次。统计排除了文本提及、
heredoc 说明和同一 PID 在 exec 前写出的 shell 文本。

开发组 helper 原始 stdout 为 160,973 字节；相关混合 bash 回传 64,850 字节，包含
其他命令，只能算全部工具文本 1,437,656 字节的 4.51% 上界。这些不是可节省 token。
另有两处摘要/head 管道把真实校验退出 2 掩盖为外层退出 0；一份读者还先把校验
JSON 写入临时文件。紧凑模式直接返回校验器原退出码，不需要外接过滤器来缩短展示。

侦察初次导入旧解析器曾新增一个未封存的 `.pyc`，已只删除该新缓存并禁用后续
bytecode。旧版 2,845 个封存文件哈希仍一致；不把侦察过程描述为绝对零写入。

## 展示契约与确定性重放

紧凑输出包含 `status`、`links_checked`、`links`。计数按引用出现次数，重复引用
不合并，也不等于实际检查次数。正常 `LINK_OK` 行省略；无执行期变化且当前全部
源码 `MATCH` 的记录保留目标、历史状态和真实命令退出码，包括非零 RED。其余行
完整保留。历史完整与当前适用性分别表达，`VERIFIED` 不表示测试全绿。

15 个固定案例各运行旧默认、新默认、新紧凑三种模式，共 45 次实际校验。默认
stdout/stderr 和退出码全部逐字节相同，所有记录目标/退出码及异常诊断按契约保留。
覆盖执行期源码变化后恢复、当前 CHANGED/MISSING、真实权限不足 UNAVAILABLE、
不安全路径、坏锚点、缺文件、坏摘要、截断、重名标题、无本地引用及顶层错误。
前后路径、字节、权限均未变，系统调用观察未见文件写入。

| 自然文档 | 完整输出字节 | 紧凑输出字节 | 原校验退出码 |
|---|---:|---:|---:|
| 当前记录正常 | 441 | 257 | 0 |
| 含历史源码漂移 | 3,181 | 1,650 | 0 |
| 含历史坏引用 | 1,389 | 1,410 | 2 |

坏引用文档取上一轮真实 trace 快照，其他文件取同项目终态；它是披露过的混合时间
夹具，不称完整历史整树。异常密集或无引用时会多约 20 字节，不硬截断。紧凑输出
不是独立可逆压缩；需要完整正常目标或逐文件 MATCH 信息时，去掉选项再只读校验。

## 新的完整开发与接手

同输入五份新对照、五份候选均正常结束，不混用旧轮试次、不重抽行为失败。
按预注册先跑对照再跑候选，顺序和未报告的后端修订也是归因限制。
两组核心原始证据均为 30/30，十份源码均通过两套独立产品检查。
核心之外仍有未绑定交付捕获的真实 unittest 调用：对照两次、候选三次；后来的
同命令记录不能替代这些实际调用，不把 30/30 扩展成全流程所有测试都已捕获。

手写摘要减少，实际校验次数没有减少。全程输入在本批下降约 25.8%、请求下降约
15.4%；试次各五份，记录布局、修复与阶段执行顺序也有不同，不能把全程用量变化
都算作该选项的收益。模型请求按原生 assistant message_end 单计，不含工具结果或
重复 turn_end。早期粗进度曾把全部 message_end 叫成请求，以上最终数已纠正。
手写摘要常在同一工具调用里完成，9 → 2 不等于减少七次模型往返。自然调用里
仍有校验器非零退出却外层过滤/聚合返回零的情况；判断时必须区分两个进程结果。

仍有明确约束失败：候选 t3/t4 在已使用新选项时仍向工程外临时目录写入并删除
文件；候选 t5 在首片 GREEN 提前实现 progress，随后恢复旧行为录 RED，再恢复
正确实现。回滚、RED 与恢复均有真实记录，不能将重建 RED 当成原开发顺序正确。
对照也有一份工程外临时写入。卡片真实回执导航为 3/5 → 4/5；未来卡提前全部
展开为 1/5 → 2/5，未达到全流程合规。

字面完整使用示例正确数为 18/20 → 19/22；只看数值及异常类型为 19/20 → 19/22。
候选 t1/t3/t5 的三个 progress 示例计算错误，对照另有一处异常消息省略尾部，
其异常类型正确。产品代码通过独立检查不能替代这些交付说明的准确性。

初始 AGENTS.md 字节未改为 4/5 → 2/5。发生变化的四份只追加既定产物位置，原
规则保留，当前授权并未要求冻结该文件；因此照录字节守卫失败，但没有把追加
本身判成越权或规则削弱。它与真正的工程外临时写入分别判读。

预选 t1–t3 各交两个新读者，共十二次自然接手。两组均为 6/6 实际取得完整 S01
RED/GREEN 原始输出、真实退出码和所测元数据，均未观察到写入、最终项目未变。
但接手成本反增：模型请求 93 → 106，总 token 2,493,315 → 2,947,456，Pi 客户端
估价 0.1916 → 0.2220 美元，未经账单核验。不能据开发阶段输入下降宣称接手降本。
增量集中在 t1 两位读者，查阅了更多源码片段和跨文档证据；没有观察到同文档
先紧凑校验、再为正常文件名回退完整校验的模式。另一个高请求读者甚至没有调用
verify，不能把整个增量归因于选项或某次回退。读者使用各自产物对应版本的运行时，
结果衡量工具和自然产物的整体接手效果，不宣称纯布局因果。

**与新展示直接相关的一项解释失败：** 候选 t3 的一个读者将 `links_checked=18`
说成“18 条全部 RECORDED”。实际返回只有八条 RECORDED，另十条正常 LINK_OK
按设计省略。它还误称 MATCH 行会被整个丢弃，实际这些记录的目标、历史状态及
退出码仍在，仅省去正常源码细节。该读者原始 RED/GREEN 取回及其退出码/计数
正确，不能把这项解释错误改写成原始检索失败，也不能说全语义门槛已过。
下一项先改进总引用、保留记录、普通引用和字段省略范围的可理解性，再验证成本。

原始取回成功也不代表每份解释正确：有读者漏看运行时已提供的封条校验算法；
候选 t2 两个读者误称旧测试不可恢复，实际可由当前文件的准确前缀核对旧哈希，
但读者没有自行证明；候选 t3 两个读者把记录的哈希封条自洽说成写入后未改，超过自校验
本身可证明的范围。隔离环境看不到旧生产者路径，也不等于原工程已删除。
