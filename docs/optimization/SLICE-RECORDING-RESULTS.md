# 从第一次检查开始记录，能减少切片文档吗？

本轮测试把“在哪里记证据”的决定移到第一次检查之前。小切片需要按时间记录命令和结果时，日志中的切片小节兼作执行回执，关闭时补上结论，任务表引用它。实验提交为 `1391bc1`，对照为 `4d12a28`。实验候选仅改 Implement 主文和紧凑回执模板。

**候选留在实验分支。** 有候选把检查集中到了一份日志，也有候选在同一文件里再次重述。两位接手者识别了同一份项目中失效的小节引用。原始写入审计另发现提前填写通过结论，交付示例重放发现计算错误。这些是本批实际风险，单次样本无法确定它们由新增规则造成。本轮开发分支保留专项评测协议和实测记录。

## 完整开发与接手

两版各跑五个新会话，使用同一双切片项目、原提示和四种隔离工具。五份候选都在第一次行为 RED 前收到新增指令。事先约定，重复明细至少减半，且至少 3/5 份候选的六项检查各只详记一次。

| 完整开发，每组五份项目 | 对照 | 候选 |
|---|---:|---:|
| 全部六项只在一个物理文件里详记的项目 | 1/5 | 4/5 |
| 全部六项各只详记一次的项目，同文件也检查 | 1/5 | 2/5 |
| 同一次实际执行在另一份主要文档里的额外明细 | 18 | 6 |
| 同一文件内另一个段落的额外完整重述 | 0 | 11 |
| 按实际执行去重后，两类额外明细合计 | 18 | 17 |
| 独立产品检查通过的项目 | 5/5 | 5/5 |
| 写出了明确但无效的历史片段引用的项目 | 0/5 | 2/5 |

每片观察 RED、首次聚焦 GREEN 和回归三种角色，共六项。有的实际命令同时承担聚焦和回归，按实际执行统计时只计一次。原始输出文件用于保留运行证据，主要文档的重述数与这些原始文件分别核对。

五次完整开发的模型请求合计为 283 → 278，累计输入为 17,300,947 → 19,396,403 tokens（含缓存），输出为 236,051 → 290,867。单次累计输入中位数则为 4,155,590 → 3,706,419。三类主要记录的写入调用为 51 → 69 次。任务间波动、实际修复和其他文档也影响这些值，尚不能将用量差异归因于单次记录的写法。

预选每组第 1–3 份最终项目，每份交给两个新会话。两组各 6/6 都找回了 S01 关键观察，并核对当前源码摘要、区分历史与当前。候选一份项目的两位读者都靠搜索补回坏锚点，另一份只有一位读者正确还原首次 GREEN 与修正的先后。工具调用中位数同为 22.5，累计输入 token 中位数由 287,437 变为 316,590.5，均含缓存。

十二次接手均无项目及私有临时目录写入，也没有重做历史测试。对照 3/6、候选 5/6 尝试探测授权范围外的原作者目录，隔离阻止其访问原项目。每组只有三个来源项目，接手结果需连同这些具体偏差解读。

## 这轮具体查到了什么

| 实际观察 | 对优化的影响 |
|---|---|
| 一份候选先记 RED、GREEN 和回归，关闭时在同一日志里把命令及结果又写一遍，任务表还再次摘要。 | 统计同文件内的重复，不能用少一个文件推断少写了一份。 |
| 一份候选的任务表引用 `trace.md#receipt-s01-v1`，实际标题没有这个锚点。反向引用的卡标题也不匹配。 | 两位新接手者都识别了原链接失效，随后搜索正文找回。查找成功仍需说明多做了搜索。 |
| 一份候选先提前改了属于 S02 的 progress，再恢复源码并重新测试才关闭 S01。随后 S02 又改到与首次 GREEN 相同的源码。 | 每次运行分别对应其源码和测试。当前摘要相同，仍须核对到底是哪次执行证明了切片关闭。 |
| 一份候选在第一片测试开始前，就写下两片 `SLICE_COMPLETE` 和 GREEN。后来删除并实际测试。 | 检查首次落盘和替换记录，保留主动修正及原始无依据声明。 |
| 一份候选的最终报告把 succeeded、failed、queued 的进度写成 33%，并解释为一项终态；实际有两项终态，应为 66%。 | 产品检查通过之后，仍要按交付代码重放文档示例并核对解释。 |

对照也有证据缺口。一份未给首次 GREEN 同时点的源码身份，另一份把后补测试的通过数量与第一次聚焦结果混在一起。上述个案都保留在原始产物和逐条评分中。
