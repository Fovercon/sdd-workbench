# 原始检查证据保留与引用优化结果

本轮处理的是：修改测试或重跑检查后，后续接手者还能否找到第一次实际执行的完整
输出，以及当时所测的源码和测试身份。它是技能使用效果的评测，不能代替真实项目验收。

开发分支保留 Implement 的四份运行文档改动，作为带已知失败的证据可靠性改进。
原始记录子指标达到 30/30，完整预注册主指标中的卡片导航要求只达到 4/5，
权限和阶段约束也有失败；整体门槛未全过，不据此认定可发布。
项目已有等价捕获方式时继续使用；否则，在
当前权限允许追加 Markdown 日志且有 Python 3.10+ 时，使用已有记录器。回执用真实
链接对应 RED/基线、GREEN 和必要回归的实际执行，保留项目要求的自足字段。
记录器 API、依赖、运行文件数量和安装行为未增加。搜索、读文件不新增记录要求。

## 新会话接手和兼容性

两版预先各选 t1–t3，每份交两个新的接手读者，使用相同的改动前运行时。修订版
六个新读者与原来固定的六个对照比较，第一版六个候选读者另行归档。实际找回
S01 RED/GREEN 完整原始输出、真实退出码和所测身份为 0/6 → 6/6；文档事实和
卡片都找回 6/6，均区分历史结果与当前适用性。这并不意味着恢复全部旧源码：
一份项目的 S01 GREEN 生产源码恰与当前文件一致，部分测试可从当前文件或前缀
核验；其余历史生产源码没有随记录保存。

读者成本同样增加：模型请求 72 → 108，总 token 1,371,624 → 3,229,816。
六份修订版读者的最终项目字节均未改，只有 5/6 全程未观察到写入；另一份擅自
创建临时校验输出，在后续调用删除，最终主动披露。最终目录干净不能抹去越界。
读者还会把隔离环境中旧绝对路径不可见过度解释为原文件不存在，不能仅据此认定引用失效。

另在修订版做三个新的固定兼容项目，覆盖单独自足回执、自定义治理目录和嵌套
回执、项目指定捕获工具。18/18 首次核心角色和 30/30 实际捕获与独立观察相符；
六份回执字段完整，也都保留观察到的完整源/测试哈希。字段完整和全长哈希分别
统计，固定输入并非逐字要求每个标识必须为 64 个十六进制字符。指定项目工具的
案例使用其八次捕获，没有改用套件记录器。三份产品和 10/10 使用示例通过，冻结输入未改。

这些是指定能力通过，仍有过程偏差：一份在核心角色之外又做了三次未交付捕获的
检查；另一份初次写下的未来卡片链接在目标创建后才可用，RED 解释后来更正；
指定项目工具案例越界创建并删除了两个临时文件。Python 缺席的环境未实测。

## 保留的限制

- 30/30 表示原始证据可追溯，不表示三十项都完成了正确的先失败后实现。一份修订
  项目提前实现 S02，首次检查意外通过，随后重建基线才得到 RED。两次均保留，
  重建 RED 不能被当成原始开发顺序正确。
- 修订版五份项目的十个稳定卡片目标与执行条款保留，但只有 4/5 项目在两片回执
  中使用可点击的卡片链接；另一份只写逻辑 ID。这是卡片导航格式的回退，不能用
  其他 223 条有效链接掩盖。另有一份提前展开未来卡片，一份越界写临时文件。
- 记录中的哈希识别所测字节，不保存历史源码副本。旧绝对路径在读者隔离环境中
  不可访问，也不能据此认定原工程中已删除或失效。
- 20ms 文档/源码采样不能单独证明每次短暂内容。选定检查另用实际原生写入和
  命令核对所测版本；不把未覆盖的其他执行扩展为已验证。
