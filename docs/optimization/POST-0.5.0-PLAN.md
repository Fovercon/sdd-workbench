# v0.5.0 后的方法优化计划

> 执行方式：按 `executing-plans` 在当前会话逐项执行；当前批次用 RED/GREEN 和一次独立评审验证。后续路线图不等于已经实施。

**Goal:** 在保留阶段职责和已有授权规则的前提下，降低小任务的流程成本，提高设计、变更、迁移和验证的可核验性。

**Architecture:** 优先补现有技能的可选参考、公开工具和有界评测；不新建主链或固定文档仪式。首先提供显式原文选择的上下文包及失效检查，再依据实际行为与成本决定如何扩展路由。

**Tech Stack:** Python 3 标准库、现有 unittest、现有 Pi/DeepSeek Flash 评测入口；不增加运行时依赖。

**Spec:** 本文件“范围与约束”及用户 2026-10-27 明确指令：排除前端共创，总结其余问题、构建计划并开始优化。具体工具接口与首批边界为实施者的技术选择，不冒充用户逐项批准。

## 范围与约束

- 基线为已发布 `v0.5.0` / `0e0fd7ac278bbdb9bd518639f03cb48b96c8c2d0`，工作分支 `codex/skills-optimization`。
- 复用独立、原本干净的发布 worktree。原始开发目录与另一 agent 的 L2/L3 工作保持原状。
- 前端共创不在本计划内；不新增技能、强制审批、通用模板套件或领域业务规则。
- 原始演示文稿、业务资料、真实评测数据库和个人路径不作为发布输入；本计划只保留方法层总结。
- 不改 live skills，不合入 main、不推送或发布，不自动 `--accept`。方法候选只有在对应 forward 和 standard 留证后才可声称完成验证。
- 来源指纹只能证明字节身份；原文含义、必要约束、充分性和行动授权仍由原有工作流核对。

## 变更归属与顺序

主要归属为方法 `PLAN` / `FLOW_FORWARD`：新增可选辅助机制，既有业务语义、阶段结果和审批合同保持。
1A 新增工具的 `build/check` 只对选择和来源做机械核对，不执行路由、测试或交接批准。
工具不自动决定哪些原文是必要的；1B 再评估是否需要扩大方法提示。后续阶段分别建立自己的当前执行卡，避免一次改多套规则而无法归因。

## 首批设计合同（1A）

`skills/sdd-workflow-router/scripts/context_packet.py` 提供 `build` 与 `check`：

- `build --project DIR --selection FILE --output NEW_DIR [--max-bytes N]`。
  选择 JSON 含 `schema: 1`、非空 `task`、非空 `sources`；每条来源含唯一 `id`、项目内相对 `path`、闭区间 `start/end`、非空 `reason`，可选 `expected_sha256` 固定已知版本。
- UTF-8 原文逐行按原顺序提供；每个来源均保留路径、范围、选择原因和完整文件 SHA256。
  不做自动摘要、必要性评分或 Token 换算；默认输出 Markdown 上限 32768 UTF-8 字节，可显式调整。
- 输出仅为新目录中的 `context.md` 与 `receipt.json`。全部输入与输出预算校验通过后才创建目录；拒绝覆盖、源路径越界、符号链接、无效范围、重复 ID、无效 UTF-8 和指定指纹不符。
- `check PACKET --project DIR` 校验相同工作区、上下文正文指纹及全部源文件指纹。
  `CURRENT` 只表示记录的字节身份一致；缺失/变化来源为 `STALE`，坏回执/正文改写/异地工作区为错误；退出码分别为 0/1/2。
- 工具不保证来源选择齐全，不授予继续实施或交付的许可，不清理宿主上下文，不代替 Handoff。
  迁移到另一路径的项目需由 Handoff 核对并重新选取，不自动重绑定旧回执。
- Router 只增加按需入口；当前上下文足够或普通局部修复时不创建包。不会把工具变成每个阶段的前置动作。

## Review Focus

- UTF-8 字节、换行及闭区间必须忠实；超预算不得把核心义务截断后报成功。
- 路径穿越、绝对路径、路径中间的符号链接和重复来源 ID 不能越过项目边界。
- 构建后修改来源、删来源、篡改正文或切到相似但不同目录都不能获得 CURRENT。
- 缺失来源、坏选择或已有输出不得写入原项目、覆盖历史包或留下“成功”回执。
- CURRENT 不等于内容充分、已阅读或已批准；字节预算不等于实际 Token 或驻留窗口。
