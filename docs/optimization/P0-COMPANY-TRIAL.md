对未约定的细节不设置隐藏门槛：动作接受合法 2xx，不要求某个内部模块/数据库模式；未明确的空重跑列表语义不据此判失败。探针修正也记录原因与原始输出。

token 只按原生完成 usage 汇总；流式增量不累加，reasoning 不重复加进 output，缓存与输入口径分列。未报告或中断请求的消耗不可推为零。不同模型、tokenizer、权限和缓存状态，没有无套件/其他框架对照，不输出效率优势或成功率。

独立源码复核与新增探针发现：

- Pi：非法UTF-8请求返回500；unpaired surrogate输入使创建500，随后整个任务列表500；最后失败项持久化后、任务finalize前真实进程退出，重启后允许的重跑动作被409拒绝；刷新后任务行只支持鼠标。它们没有被原30项/父级10组验收覆盖。
- Pi第一次反馈修复虽让该恢复路径能执行，却把paused直接重跑写入Spec/Plan和代码，违反冻结接口“paused先resume、仅partial可rerun-failed”。原补丁、测试绿和较弱父级探针的绿均保留；收敛审查退回，另启动第二次有界修复。不能把“接口给出的动作能调用”替代“动作符合原合同”。
- Codex：20,001项中20,000成功、1待执行，直接投影却舍入成100%进度，违反原有不补满规则，已独立复现并启动有界修复。
- 输入缺口：首轮没有明确运行中成功率分母、pending是否含running，两者选择不同。控制方回到固定来源的 `service/orchestration/common/task/queries/governance_outcome.py` 核对：成功率以processed为分母、pending不含running。新增有来源澄清，记录为输入不足，不对首轮施加隐藏验收。Codex需要对齐，Pi原实现已相符。
