# 面向公司推广的基线审视

日期：2026-10-25。基线：v0.2.1，提交 `6de58e3b028c8252c2b52ee7fd49a404b4def7da`。
这是推广准备审视，范围包括入口、12 个技能的职责与规则布局、现有验证、安装支持和比较定位。
READ 表示源码/文档证据；风险等级是后果评估，不等于已经观察到用户失败。
本轮第一步的行为结果另记，历史发布通过不自动成为优化后的验证。

**判断：目前适合有维护者参与的受控试点，没有证据支持全面推广或“优于其他框架”的结论。**
已有的阶段边界、授权来源、证据身份和恢复规则值得保留；新增口号、更多 skills 或更多模板不能解决以下缺口。

## 不能作为区别或优势的共同能力

以下是 2026-10-25 官方 README 的固定提交快照；只比较公开机制，没有安装或跑同题任务。
这些机制能证明“有此入口/描述”，不能证明实际效果。

| 框架和固定源 | 可核实机制 | 对本项目的约束 |
|---|---|---|
| [Spec Kit](https://github.com/github/spec-kit/blob/67e0f7294e6e728ab60bf7b4590deb470448bc2d/README.md) | 规格→计划→任务→实施→收敛，另有独立 bug 入口；组织 preset、bundle、私有 catalog、离线来源 | 不能宣称只有我们能修 bug 不走全流程、支持组织规则或多 agent；企业分发治理需要补课 |
| [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/6d04a1b58dedc95729d34e4f223d9d483aae210a/README.md) | 存量项目变更、默认 explore/propose 入口、可选扩展流程；共享 Stores 标为 beta | 不能宣称轻量分流、brownfield、共享规格或看板是独创；其 beta 声明不能外推为稳定性差 |
| [Superpowers](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/README.md) | 讨论/设计、计划、TDD、子 agent 或单会话执行、评审和分支完成；小改动可在聊天中确认 | 不能靠“有技能、TDD、两轮审查、多 agent”区分；需实测本方案的流程成本和权限/证据链 |
| [BMAD](https://github.com/bmad-code-org/BMAD-METHOD/blob/61e01f82644c4bb533750cfa0d6d61ab61d2cc9b/README.md) | 按变化选择深度、领域角色协作和持续交付上下文；main 自述 v7 preview，稳定线单列 v6.12 | 不能用多角色/按风险缩放作为独有优势；比较必须分清预览线与稳定线 |

我们的**定位假设**：把用户授权来源、精确合同/源身份、审查证据、交付后核验和中断恢复
作为一个可审计的工程闭环；让局部工作也能使用其中必要的部分。各机制的已有实现可在
Router closed-loop、Finish readiness 和 Context handoff 中找到；“组合更适合某类公司任务”仍待比较验证。

有可能适合的场景：多会话接续、已有批准规格的变更、记录保全/恢复、需要知道“谁授权、
依据哪个版本、实际验证了什么”的交付。对于纯探索、一次性文案/小改动，不应强行生成合同链。
若同题测试没有可观察收益，应收缩定位和流程，不能通过增加术语维护“优势”叙述。
