# Domain quality profile evaluation plan

> Execute inline with `executing-plans`; one fresh whole-branch review at completion.

**Goal:** Measure whether Verification Design can turn an approved synthetic domain
contract into a reproducible quality profile without confusing JSON validity,
semantic correctness, reviewer agreement or execution evidence.
**Architecture:** Extend the existing workflow preparation/protection protocol with
two states of one small summary-quality fixture. Reuse Pi and usage measurement;
no new skill, judge service, runtime tool or mandatory project artifact.
**Tech Stack:** Python standard library, unittest, registered DeepSeek Flash.
**Spec:** POST-0.5.0-PLAN.md roadmap5 and the user's instruction to continue the
next optimization. Existing inline execution and local-only development continue.

## Constraints and acceptance

- BASE `2303366`, isolated `codex/skills-optimization`; preserve primary checkout,
  L2/L3, live skills, main, version and tags. No push/release or baseline acceptance.
- Only synthetic repair-request summaries; no real business data. A domain policy
  explicitly owns meaning and gates; a second state leaves adjudication authority
  unresolved. Technical choices here are maintainer choices, not user decisions.
- Design-only actor: write `VERIFICATION.md`, inspect inputs/runtime; no test
  implementation/execution, model calls, fixture relabeling or project edits.
- Both states use the same prompt and inputs except `DOMAIN.md`. Data roles and
  versions are explicit; sealed future evaluation content is not available to the
  actor. A manifest is not evidence that a held-out run happened.
- Five baseline repeats/state; inspect every completed call/final and material
  contract/profile sections, not a regex-only semantic score. Preserve failures.
- Consider at most one small runtime candidate only for a recurring demonstrated
  omission. Baseline competence is a valid result. Retention requires all core
  invariants, affected paired forward and exact-snapshot standard without --accept.
  Otherwise retain useful protocol/evidence only, without a claimed method gain.

## Review focus

1. Valid structure can contain false commitments or altered quantities; quality
   cannot be inferred from parse success or historical schema-only reports.
2. Equivalent paraphrases are valid; reference wording is not an exact-text oracle.
3. Calibration samples and development examples are not held-out evidence. Record
   actual sample/split/domain/rubric/model identities, denominators and limitations.
4. Disagreement stays visible; an unresolved adjudication owner cannot be replaced
   by averaging votes, a sole self-judge, a default pass or an invented threshold.
5. Revision1 labels cannot certify revision2 meaning. Design remains DESIGNED;
   structural guards do not judge semantic adequacy or enforce OS isolation.
